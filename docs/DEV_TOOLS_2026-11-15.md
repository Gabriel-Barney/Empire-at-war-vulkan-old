# Development tools survey (2026-11-15)

**Question:** which tools that the project does not use yet would help development now, given the current focus (parity
tier 1 and 2, plus crashes, hangs and save corruption) and the rules in `CLAUDE.md` (project-local installs, no new
`engine/` dependency without Gabriel's approval, Windows x64)?

## Answer

Ranked by value for the current focus and by cost. Items 1 to 3 need **no download**: the tools are already in
`toolchain\llvm` (LLVM 20) and are simply not wired up.

| # | Tool | What it would catch or show | Cost | Confidence |
|---|---|---|---|---|
| 1 | **libFuzzer** (`clang_rt.fuzzer-x86_64.lib`, already in `toolchain\llvm\lib\clang\20\lib\windows`) | Crashes and hangs in the parsers that read mod files: MEG, ALO / ALA, XML, the Lua chunk loader, save loading. Mods are a near-full compatibility target, so malformed input is real input | One fuzz target per parser plus a `build_fuzz.cmd`; clang only, needs ASan, `/MT`, no `/INCREMENTAL` or `/DEBUG` link [1] | CONFIRMED (lib present; Windows support per [1]) |
| 2 | **clang-tidy** (`toolchain\llvm\bin\clang-tidy.exe`, `run-clang-tidy`) with a small `.clang-tidy` | Real-bug checks the compilers do not give: `bugprone-use-after-move`, `bugprone-unchecked-optional-access`, `bugprone-dangling-handle`, `bugprone-integer-division`, `concurrency-mt-unsafe` [2]. clangd (already set up) shows the same checks in the editor once the file exists | One config file plus a `tools\lint` runner over `compile_commands.json`; start with `bugprone-*` and a few `concurrency-*` / `performance-*`, warnings-as-errors only after the first clean pass | CONFIRMED (exe present; checks per [2]) |
| 3 | **Source-based coverage** (`llvm-profdata.exe`, `llvm-cov.exe`, `clang_rt.profile-x86_64.lib`, all present) | Which retail rules in `engine/` no test reaches; a per-module coverage report for the sim set makes parity gaps visible before a playtest finds them | A `build_coverage.cmd` on the clang tree: `-fprofile-instr-generate -fcoverage-mapping`, run ctest with `LLVM_PROFILE_FILE=%m-%p.profraw`, then `llvm-profdata merge` and `llvm-cov report` / `export` [3] | CONFIRMED (tools present; flags per [3]) |
| 4 | **Crash minidumps** written by the Command Center for `alamo_game.exe` (Win32 `MiniDumpWriteDump`, DbgHelp, part of Windows) | A crash in Gabriel's playtests becomes a `.dmp` an agent can open in the WinDbg already in `toolchain\re`, instead of a description. Needs symbols for the shipped build (`/Z7` + `/DEBUG` PDBs; Release has none today, `PERF_AUDIT_2026-11-07.md` L6). No new dependency | CONFIRMED (API per [4]); design UNVERIFIED |
| 5 | **ꟻLIP** (NVIDIA, BSD-3, `pip install flip-evaluator`, CLI `flip`) [5] | Perceptual diff of port vs retail screenshots for visual parity (tier 1 look): an error map weighted by what a viewer notices, next to the per-pixel `tools\visual\png_diff.py` | A pinned wheel in `toolchain\venv`, a `--metric flip` option in `png_diff.py` or a separate script. Tool, not an `engine/` dependency | CONFIRMED (licence and CLI per [5]) |
| 6 | **GFXReconstruct** (LunarG, MIT) [6] | Capture and replay of the port's own Vulkan frames (`VK_LAYER_LUNARG_gfxreconstruct`, `gfxrecon-replay`), for a renderer bug seen on Gabriel's machine that an agent then replays. RenderDoc is out of scope (`DECISIONS.md`, 2026-10-29); apitrace covers retail's D3D9 side only | Project-local layer install like `toolchain\vvl`; needs Gabriel's go-ahead because it reopens the GPU-capture question | CONFIRMED (Windows Vulkan capture and replay supported per [6]) |
| 7 | **Radeon GPU Detective** (AMD; the dev machine has an RX 9070 XT) | GPU crash / TDR dumps for Vulkan (added in RGD 1.1 [7]): which shader and command were in flight | Free download, driver put in Crash Analysis mode via Radeon Developer Panel [7] | Vulkan CONFIRMED [7]; RDNA 4 support UNVERIFIED (AMD's RDNA 4 post names the suite as updated but lists RGD only for D3D12 [8]; settle by reading the current RGD release notes) |

**Recommendation:** do 1, 2 and 4 first (crash and bug finding, inside the current focus, no download). 3 and 5 support
parity work. 6 and 7 only when a renderer or GPU crash needs them; 6 needs a decision row.

## Already in place (not proposed again)

MSVC + clang 20, UBSan / ASan (`build_asan.cmd`; no TSan on Windows, races covered by the worker-count CRC tests,
`BUILD.md`), sccache and the shared PCH, clangd, Vulkan validation layers (`toolchain\vvl`), apitrace + DXVK for retail
captures, Ghidra + ReVa, Frida, TTD and WinDbg (`toolchain\re`), the in-engine tick profiler, `tools\parity`,
`tools\visual`, Rust with clippy / rust-analyzer for the launcher.

## Fit

- **Determinism (rule 3).** None of the tools changes sim code or its build. Fuzz, coverage and tidy builds use their own
  build trees and never feed goldens; coverage instrumentation changes timing only.
- **Dependencies (rule 2).** Items 1 to 4 add nothing to `engine/` (libFuzzer targets live under `tools/` or a test dir and
  link only in the fuzz tree; DbgHelp is a Windows system library used by the launcher). ꟻLIP and GFXReconstruct are tools,
  installed under `toolchain\` with a pinned version and a setup step (rule 5).
- **libFuzzer status.** It is in maintenance mode: bug fixes, no new features [1]. Enough for parser fuzzing; the
  Phase 3 review already ran about 300k ASan / UBSan fuzz iterations by hand (`PHASE3.md`), so the targets have a starting
  corpus idea (real game files from the VFS).
- **Paused by the current focus (tier 3, not proposed now):** Tracy or Superluminal (CPU / GPU profiling), vcperf / Build
  Insights and include-what-you-use (build speed), Radeon GPU Profiler. `PERF_AUDIT_2026-11-07.md` already covers them.
