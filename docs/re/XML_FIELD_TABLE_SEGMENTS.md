# xml_field_tables.md segment errors (mcx4, 2026-11-18)

`docs/re/xml_field_tables.md` is generated by `tools/re/make_docs.py`. It groups the exe's field descriptors into one
segment per object class, and a few segments pick up descriptors from a neighbouring table. Each row below is listed
under a class that never reads it. The field belongs to the class named here: the retail XML writes the tag only inside
that class's elements, and the offset fits that class's record. The tag ledger settles such a row as `misfiled` (the
`MISFILED` table in `engine/objects/tools/gen_tag_ledger.py`) only while the port reads the real owner's field. A row
whose real owner the port does not read stays an honour gap under its listed name until a reader exists.

| Listed as | Really | Evidence |
|---|---|---|
| `MousePointer.Icon_Name` | `GameObjectType` / `Faction` / special-ability `Icon_Name` | MousePointers.xml writes no `Icon_Name`; all 1013 FoC uses are in object type, faction and ability elements |
| `MousePointer.Apply_To_All_Allies` | ability field (`Battlefield_Modifier`, `Enhance_Defense`, `Garrison_Upgrade`, `Weatherproof`, `Bounty` abilities) | FoC writes it only inside those ability elements |
| `HardwareConfiguration.Apply_To_All_Allies` | `Garrison_Upgrade_Ability` (and the abilities above) | GraphicDetails.xml writes none; the descriptor at +0x178 sits after the hardware fields in the same table run |
| `MousePointer.Affects_All_Allies` | ability field (`Enable_Radar_Ability`, `Enable_Ability`) | FoC writes it only inside those ability elements |
| `MousePointer.Ability_Name` | ability field (`Enable_Ability`, hero clash `Special_Ability_Action`) | FoC writes it only inside those elements |
| `HardwareConfiguration.Type` | ability `Type` (+0x18 of the ability record) | GraphicDetails.xml writes no `Type`; the 1606 FoC uses are ability / sub-object `Type` elements |

`HardwareConfiguration.Additional_Garrison_Units` (+0x180) is `Garrison_Upgrade_Ability`'s field (UpgradeObjects.xml
`RL_` / `EL_` / `RS_` / `ES_More_Garrisons_L1_Bonus`; GraphicDetails.xml writes none). The tag exists under no other
class, so the port's ability parser (`ability_data.cpp`) settles the row as consumed under its listed name, with no
`MISFILED` entry (mcx4-tac2, 2026-11-18). The ability's vtable 0x8c7f20 (read from the exe):
- slot 29 0x6fffa0 warns when the list is empty;
- apply (slot 30, 0x6ffc60) appends each type to the start-force list (player +0x2a8) of the owner, or with
  `Apply_To_All_Allies` of every player allied with it;
- remove (slot 31, 0x6ffe30) takes one entry of each type out again;
- can-apply (slot 5, 0x6ffdb0) passes only in a skirmish (0x28afb0). So the types join the skirmish garrison
  re-delivery (SKIRMISH_SETUP §2.4). Port: `SpecialClass::GarrisonUpgrade`.

Rows of the same kind that stay gaps, because the port reads no real owner yet:

- `Tractor_Beam_Attack_Ability.Lightning_Effect_Name` / `Start_Lightning_Frame_Number`: `Force_Lightning_Ability` fields
  (+0x190, read by 0x6fdc40, ABILITY_PARTICLES.md §9). FoC writes them in the Force_Lightning, Hack and Repair
  abilities, never in Tractor_Beam. The port does not read them.
- `TacticalCamera.Intensity` / `Radius` / `Diffuse`: `LightSource` fields (offsets 0x0 / 0x4 / 0x10).
  TacticalCameras.xml writes none. The port reads no LightSources.
