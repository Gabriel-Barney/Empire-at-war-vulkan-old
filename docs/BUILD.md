# Build, test and gate

The full detail of building, testing and the gate. `CLAUDE.md` keeps the short rules agents must follow; everything else is here (moved verbatim on 2026-11-06 from `CLAUDE.md` "Build and test" and the build rules of "Platform and compilers", and from `docs/PHASE4.md` "Worker-count check" and "Sanitizer limits").

## Which checks a change needs (from "Platform and compilers")
- Two compilers: MSVC ships, clang checks.
- Every change: MSVC build + tests. Changes to sim code (everything in `engine/` except render, audio,
  video and UI): also the clang build + tests, including the CRC selfchecks. Changes to `engine/jobs` or
  other threading code: also `build_asan.cmd` (clang UBSan by default; `set ALAMO_SANITIZE=address` for ASan, which then runs with `-asan-stack=0` (heap and globals only) because stack instrumentation crashes catch handlers on this toolchain, see "Sanitizer limits" below; the default module list is the 11 sim modules; no TSan runtime on Windows, so races are covered by the per-worker-count CRC tests).
- Shaders are compiled by DXC (`toolchain\dxc`) to SPIR-V; the C++ compiler choice doesn't affect them.

## Build and test (moved from CLAUDE.md)
- Line endings: `.gitattributes` keeps text files LF in the working tree too (test data and scenario outputs are compared byte for byte); `.cmd` / `.bat` / `.ps1` are CRLF.
- Screenshot diffs (2026-10-30; wr1 t07: no stored baselines): `tools\visual\visual_check.cmd [REV]` compares REV's game smoke screenshots (default HEAD) with its parent's, both from the smoke scenarios' cached results (`tools/visual/visual_builds.py`; a commit not cached is built and run, needs game data and a GPU). Mismatches get diff images in `logs\visual_diff\<scenario>\`. The engine is `tools/visual/png_diff.py` (`--selftest`). Not in the gate: it needs the GPU and game data.
- Generated files (Gabriel, 2026-11-07): a tool writes its output only into an ignored folder (`out/`, `work/`, `build-*`, `logs/`, or one added to `.gitignore` with the tool), never next to tracked files; about 35,000 lines of tracked generated files had to be cleaned up (roadmap groups cu17 / cu18). `tools\land_on_dev.cmd` runs `tools\lint\check_tracked.py` before it pushes, and `build_gate.cmd` runs it for the release: a file the landing adds fails when it is over 512 KiB (128 KiB for `.json` / `.csv` / `.xml` / `.txt` data outside `tests/` and `*/testdata/`), sits in an output folder, is a build product (`.obj`, `.exe`, `.log`, `.spv`, ...) or is binary outside the test-data and reference folders. Files already tracked are not checked. A file that must be tracked anyway gets a glob and a reason in `tools/lint/tracked_allow.txt`. Selftest: `check_tracked.py --selftest`.
- Version control (2026-10-30): the project is a git repository; commit before and after each agent task. Branches (2026-11-06): work goes to the long-lived `dev` branch, not a new branch per task, group or session; `main` gets `dev` by PR after `build_gate.cmd` passes on `dev` (rules in `CLAUDE.md`, "Branches"; `tools\land_on_dev.cmd` lands a session branch on `dev` safely). Build trees, logs, `toolchain/`, game data (`Data/`, `extracted/`), `re_reference/` and probe captures are ignored; `roadmap-store/` is its own repository. Remotes (both private, 2026-10-30): engine `https://github.com/Gabriel-Barney/Empire-at-war-vulkan.git` (`origin`, integration branch `dev`, released branch `main`; push after each task); roadmap store `https://github.com/Gabriel-Barney/Empire-Vulkan-Brenach.git` (`roadmap_store.py` pushes by itself after every write and build record; `python roadmap-store/roadmap_store.py sync` checks it). On a new account or machine: `git clone` the engine repo, `git clone` the store into `roadmap-store/`, then rebuild `toolchain/` with `toolchain\*.cmd` and unzip game data (these are not in git).
- Main build: run `build_msvc.cmd` from the project root. It configures `build-msvc\`
  with the local toolchain, builds everything and runs ctest. Read `logs\msvc_configure.txt` and
  `logs\msvc_build.txt`; the run is finished when `msvc_configure.txt` ends with `BUILD_DONE`.
- Every build script records its result on the roadmap (`docs/ROADMAP_PROTOCOL.md`, "Build records").
- Build speed (bo1, 2026-11-13; numbers in `docs/PERFORMANCE.md`, "Build times"): `python tools/benchmark/build_times.py` repeats the clean / one-.cpp / one-core-header measurements. The shared PCH (`engine/pch`, `-DALAMO_PCH`) is on by default only when no compiler cache is active, because sccache cannot cache PCH compiles. With the cache on, `CMakeLists.txt` forces a per-checkout alias header into every compile so cache entries match only inside one checkout; this replaces the old "build worktrees with the cache off" advice (`.ninja_deps` no longer records another worktree's headers; if a no-op build rebuilds hundreds of targets, run `ninja -d explain` and look for foreign paths). `build_gate.cmd` runs clang only when `tools/lint/gate_scope.py` finds sim code in the change and ASan only for `engine/jobs` / `engine/core` / threading code, any doubt runs both (`ALAMO_GATE_ALL=1` forces both; the summary prints `SKIP` with the reason). `land_on_dev.cmd` accepts a passing stamp whose build-source hash equals HEAD's (a docs / roadmap-only merge does not rebuild). `clean_worktrees.cmd --trees` keeps `build-wt-msvc` in every kept worktree.
- Clang check: `build_clang.cmd` (project-local LLVM 20, MSVC ABI and headers, adds `-Wconversion -Wshadow`; logs `logs\clang_*.txt`, finished when `clang_configure.txt` ends with `BUILD_DONE`).
- One module only: add `-DALAMO_ENGINE_MODULES="<module>"`. Since wr3 t06 (2026-11-21) the configure adds the modules the configured targets link (`ALAMO_ENGINE_MODULES: added for links: ...`; unconditional links only, `if(TARGET ...)` features stay off) and stops on a name that is not a module (`game`, `tactical_combat`, a PowerShell `--%` passed through), naming the module meant. Before, such a list configured fine and failed later with "Cannot open include file": all 54 of those failures of 2026-11-14 to 21 (core left out 33, another dependency 12, a non-module name 8, ui's abilities header 1).
- Data-driven tests read `ALAMO_FOC_DATA` / `ALAMO_EAW_DATA` (folders containing `Data\XML`; unzip `extracted/*.zip`). They skip when unset, so a pass without them proves less. `build_msvc.cmd`, `build_clang.cmd`, `build_asan.cmd`, `build_agent.cmd` and `build_module.cmd` (the last two since 2026-11-02) call `tools\test_env.cmd`, which defaults them to `F:\SteamLibrary\steamapps\common\Star Wars Empire at War\corruption` and `...\GameData` when unset and the folder exists (2026-10-30); tests print a skip message and exit 0, so each script ends its log with `skips: data=N gpu=N other=N` from `tools\lint\ctest_skips.py` (reads ctest's JUnit file; `--list` names them). Last full run: 1 data skip (`alamo_lua_players_tests`, no PerceptualEquations folder), 0 gpu.
- Tick profiler (2026-10-30, OPT1): `alamo_headless ... --profile [--profile-out FILE] [--profile-budget MS]` prints per-tick p50/p99/max, per-zone time and the 20 worst ticks; baselines and the budget are in `docs/PERFORMANCE.md`; `bench_msvc.cmd` re-runs them. Wall-clock only: never let sim code read a profiler value.
- Scheduled gate (Gabriel, 2026-10-30: this PC runs it; on `origin/dev` since 2026-11-12): `tools\gate_scheduled.cmd [checkout]` fetches origin, forces the locked, detached worktree `.claude\worktrees\gate-dev` (made on the first run with junctions to `Data`, `extracted`, `toolchain` and `roadmap-store`; `clean_worktrees` keeps it because it is locked) to `origin/dev`, runs `build_gate.cmd` there, appends `<sha> dev gate exit N` to the main checkout's `logs\gate_history.txt` and copies the summary to `logs\gate_dev_summary.txt`. It skips with exit 3 when that `origin/dev` commit already passed, exits 4 when the setup fails, and never touches the main checkout's branch or files (before 2026-11-12 it gated whatever the main checkout had checked out and skipped on uncommitted edits, so `dev`'s tip went ungated for days). `set ALAMO_GATE_DRY=1` checks the setup without the gate. `tools\install_gate_task.cmd [HH:MM]` copies the script to `<main checkout>\logs\gate_task\` (gitignored; so a checkout never changes it while it runs) and writes `gate_task.cmd` beside it, a launcher with the main checkout baked in that logs each run to `logs\gate_task\gate_last_run.txt` (start line, the gate's output, exit code); the per-user nightly task `AlamoGateNightly` runs that launcher with no arguments (default 03:00, no admin, runs while logged on; remove with `schtasks /Delete /TN AlamoGateNightly /F`; `--no-register` writes the files only). Rerun the installer after `gate_scheduled.cmd` changes. Never install it under `%LOCALAPPDATA%` / `%APPDATA%`: commands run from the Claude desktop app (an MSIX package) have AppData writes redirected to `AppData\Local\Packages\Claude_*\LocalCache\`, which Task Scheduler does not see; that is why the task exited 1 within a second every night from 2026-11-13 and wrote no history line (ref6 t07, found 2026-11-20); a run that writes no `gate_history.txt` line is read in `gate_last_run.txt`. Missed nights (wr0 t04, 2026-11-21): each run appends ` (missed N nights (first..last))` to its history line when days since the previous line have none (`tools\lint\gate_nights.py`, `--selftest`; the installed copy reads it from `origin/dev`, since `logs\gate_task\` holds only the gate script).
- Landing queue and verifier (wr2, 2026-11-21; replaces the landing check below as the way onto `dev`): `python -I tools/gate/land_queue.py submit [REV]` queues the commits `merge-base(REV, origin/dev)..REV` of your checkout (entries in `<main checkout>\.cache\land-queue`, tips pinned by `refs/land-queue/<id>`; `status [<id>]`, `withdraw <id>`). The verifier (`tools/gate/verifier.py`, installed by `tools\gate\install_verifier_task.cmd` as the per-user task AlamoVerifier, every 5 minutes, `run --once`; log `<main checkout>\logs\verifier_task\verifier_log.txt`) works in its own locked worktree `.claude\worktrees\verifier` (trees `build-verify-*`, used by no writer): it rebases the waiting entries onto `origin/dev` (a conflict rejects that entry), runs `build_agent.cmd msvc verify all` (fast tier), the clang fast tier when sim code changed, `tools/goldens/behaviour_check.py range` (strict: a sim commit without a `Behaviour:` trailer, or a moved column it did not declare, fails) and, for sim code, `behaviour_check.py compilers` on the two verify trees (each scenario's clang result equals its MSVC result; wr1 t07), and fast-forwards `dev`. Several waiting entries are checked as one batch; a failing batch is bisected by prefixes, the good prefix lands and only the bad entry is rejected. Each decision writes `<id>.summary.txt` beside the entry. Only the verifier and the nightly gate write roadmap build records (`ALAMO_RECORD_BUILD=1`); iteration builds go to `<main checkout>\logs\build_records\` (`tools/lint/record_build.py`). Nightly deep run: `tools\gate_scheduled.cmd` then `tools/gate/nightly_triage.py` bisects each new failure over the night's landings and files it in group `ngt1` (a known one gets a "seen again" line; mappings in `logs\nightly_state.json`), and sets the roadmap page's build line. Selftests: `land_queue.py`, `verifier.py`, `nightly_triage.py`, `record_build.py` `--selftest`.
- Two writer checkouts and the path guard (wr4 t01 / t02, 2026-11-21): `tools/gate/writer_setup.py create` makes `.claude\worktrees\writer-sim` and `writer-nonsim` (scratch branches `claude/writer-sim` / `claude/writer-nonsim` from `origin/dev`, junctions, a role file `.alamo_writer`, a worktree lock so the cleanup tools keep them); `warm` builds their MSVC and clang agent trees; `sync <checkout>` rebases the scratch branch onto `origin/dev` after a landing (commits already on `dev` drop out). `.claude/settings.json` runs `tools/lint/path_guard.py --hook` before every Edit / Write: the non-sim checkout may not edit sim code (engine modules other than render, audio, video, ui), and no session may edit the verifier's checkout; the block names the path and the owner. Selftests: `writer_setup.py`, `path_guard.py` `--selftest`.
- Landing check (2026-11-12; retired with `land_on_dev.cmd` by wr2 t04 on 2026-11-21, it still applies when Gabriel lands directly with `ALAMO_LAND_DIRECT=1` while the verifier is down): `tools\land_on_dev.cmd` pushes only a merged HEAD that has a passing MSVC build of every module with the fast tier or all tests. `build_agent.cmd` and `build_msvc.cmd` stamp each tree (`tools\lint\verified_build.py begin` / `pass`: HEAD, clean or not, modules, test filter; `<tree>\verified.json` only after a pass on a clean tree); `land_on_dev.cmd` accepts a `build-wt-msvc` or `build-msvc` stamp for exactly the merged HEAD, or a change to `docs/`, `*.md` or `.claude/` only, and otherwise runs `build_agent.cmd msvc wt all` itself. A pass before the merge with `origin/dev` does not count: two branches that each pass can break `dev` together. clang, ASan and slow tests stay the lane's job. Selftest: `verified_build.py --selftest`. Since wr1 t07 it then runs `tools/goldens/behaviour_check.py range origin/dev HEAD` (strict) instead of the slow golden checks.
- Build-tree names (ref3 t03, 2026-11-19): `tools/lint/build_trees.py` is the one place that names build trees (`build-<tree>-<compiler>` for `build_agent.cmd`, `build-msvc` / `-clang` / `-asan` / `-cov` / `-fuzz` for the main scripts, `build-<module>` for `build_module.cmd`) and finds an exe in them (`find_exe`: `build-wt-msvc`, `build-msvc`, `build-wt-clang`, `build-clang`; `--main-first` for the benchmarks). Python tools import it; the `.cmd` scripts ask it (`build_trees.py name agent wt msvc`, `exe alamo_headless.exe`). `build_trees.py check` (run by `build_agent.cmd`) refuses a tree name spelled in code anywhere else under `tools/` or in a root `.cmd`. Selftest: `build_trees.py --selftest`.
- Edit-time compile check (wr3 t02, 2026-11-21; replaced the string-literal hook): `.claude/settings.json` runs `tools\lint\compile_check.py --hook` after every Edit / Write of a C++ file (the script of the edited file's own checkout). It runs the string-literal pass, then compiles the translation unit syntax-only on MSVC (`/Zs`) and clang (`-fsyntax-only`) at once with the exact flags of the checkout's `build-wt-msvc` / `build-wt-clang` `compile_commands.json` (so `/W4 /permissive-` and clang's conversion and shadow warnings apply); a header edit checks up to two includers from the tree's dependency log (same-stem source first). A source missing from the build is reported ("not in the build: list it in its CMakeLists.txt"). Findings reach the agent as hook output (exit 2); it never blocks an edit. Needs both trees configured once per checkout (`build_agent.cmd clang all configure`, and `msvc`); the MSVC environment is cached in `<tree>\msvc_env.json`. Measured 2026-11-21: median 1.2 s over 16 files (max 2.4 s); `--repro` compiles the fifteen most common compile errors of the build records (C1083, C2039, C2065, C3861, C2027, C2143, C4430, C2664, C2737, C2146, C2440, C2059, C2653, C2248, C2001) and the C4244 / `-Wconversion` warning: all caught on both compilers. Link errors (LNK1104 locked exe, LNK2019) are outside it. `--selftest`.
- String-literal pre-check (2026-11-12): `tools\lint\check_string_literals.py` finds string and character literals that do not end on their line (MSVC C2001, the most common compile error in the build records: an edit turned a `\n` escape into a real line break). `build_agent.cmd` and `build_module.cmd` run it on the C++ files changed against `origin/dev` before they build (about a second; nothing is built or recorded when it fails), and the edit-time compile check below runs it first. `--all` scans every tracked file (0 findings, about 6 s, 2026-11-12); `--selftest`.
- Pre-merge gate: `build_gate.cmd` runs the MSVC build, the clang build and `build_asan.cmd`, records each on the roadmap, prints `logs\gate_summary.txt` and exits 0 only when all three pass with 0 warnings (about 4 minutes when little has changed).
- Tests run in parallel (2026-10-30): `build_msvc.cmd` / `build_clang.cmd` use `ctest -j 8`, `build_agent.cmd` / `build_module.cmd` use `-j 4`. A full run takes about 110 s on MSVC and 100 s on clang (was about 640 s and 590 s). If you run ctest by hand, pass `-j` too and set `TMP` / `TEMP` to `<build tree>\tmp`.
- Test slots (2026-11-12): every build script runs its ctest through `tools\lint\test_slot.py`, which lets at most `ALAMO_TEST_SLOTS` (default 2) test runs go at once on this machine, across all checkouts and worktrees; a third run waits, prints who holds the slots and every 5 minutes, and runs anyway after `ALAMO_TEST_SLOT_WAIT` seconds (default 5400). Before this, about 25 sessions saw tests time out when several full runs shared the 16 cores, then pass alone. A slot is a byte lock in `%LOCALAPPDATA%\AlamoTestSlots`, dropped by Windows when its process ends, so a killed run never keeps one. `test_slot.py --status` shows the holders; `set ALAMO_TEST_SLOTS=0` turns the limit off for one shell; `--selftest`. A ctest you start by hand does not take a slot unless you prefix it the same way.
- Build state and repeat check (2026-11-13): in the build records of 2026-11-10 to 12, 92 of 359 failing test runs failed exactly the same tests as the run before in the same tree, and a record could not say which code it built. Every build script now runs `tools\lint\build_state.py begin <tree>` first: `<tree>\build_state.json` gets the commit, worktree, branch, dirty flag, a source hash (HEAD + uncommitted tracked edits + untracked files), the module list and the test filter. `build_summary.py --state <tree>\build_state.json` adds the outcome, and `record-build` copies the fields into the build record (`ALAMO_BUILD_EXTRA`; `docs/ROADMAP_PROTOCOL.md`, "Build records"). `build_agent.cmd` and `build_module.cmd` pass `--refuse-repeat`: when the last run in the tree FAILED on the same source, modules and tests, they print that run's summary again and exit 3 without building. Set `ALAMO_RERUN=1` for a flaky test or a changed environment (game data, toolchain). `build_module.cmd` now exits with the summary's code. `--selftest`.
- No golden drift (wr1 t07, 2026-11-21; replaces the 2026-11-13 golden-drift split): no test compares a stored derived golden, so `build_summary.py` reports every failed test as a real failure. A behaviour change shows in the verifier's `Behaviour:` check (`tools/goldens/behaviour_check.py`, skill `behaviour-check`), never as a failing test. Build records keep `failure_kind` (configure, compile, warnings, test, unfinished, other) and `real_failures`; `golden_drift` stays as an empty list. `--selftest`.
- Affected tests (wr3 t01, 2026-11-21; replaced the 2026-11-13 changed-module mapping): `build_agent.cmd <compiler> [tree] <modules> changed` runs the fast-tier tests that depend on a file changed against `origin/dev` (commits, edits, untracked files). `tools\lint\affected_tests.py` reads the tree's build graph: each test's executables (its command and any tree `.exe` in its arguments) through `ninja -t inputs` to their sources, each source's headers through `ninja -t deps`, plus every repo file its command line names (data, goldens, scripts). So a tactical header change also runs the apps scenario tests that link tactical, and a goldens file runs its test. A module `CMakeLists.txt` selects the tests built from that folder; `engine/CMakeLists.txt`, `engine/test_support/`, the top-level CMake or `cmake/` select every test; nothing selected runs the whole fast tier. The graph is cached in `<tree>\affected_graph.json` until `build.ninja` or `.ninja_deps` change. `--evaluate N` checks the last N golden changes on `dev` (2026-11-21: 30 of 30 selected by the engine changes behind them); one-module commits select a median 48 of 219 fast tests (apps 3, tactical 106, ai 93, objects 160). Run the whole fast tier before landing (the verifier does). `--selftest`.
- Golden-only merge conflicts (2026-11-13; removed by wr1 t07 with the stored goldens and `tools\lint\golden_merge.py`): there are no golden files left to conflict in.
- Pre-approved commands (2026-11-12): `.claude/settings.json` allows, without a prompt or an auto-mode check, `python -I tools/gate/land_queue.py ...` (wr2 t04, 2026-11-21, replacing the `land_on_dev.cmd` spellings; a session's `git push` to `dev` is denied, the verifier pushes from its scheduled task outside any session), `python -I tools/worktree/delete_merged_branch.py <claude/...> ...` (deletes remote `claude/*` branches only when their tip is in `origin/dev` or `origin/main`, and logs the SHA to `logs\deleted_branches_<date>.txt`), `python -I tools/worktree/stop_tree_procs.py [--dry-run] [build-tree ...]` (stops processes running from this checkout's own `build-*` folders, never another worktree's) and `test_slot.py --status`. Use these instead of `git push origin --delete`, `taskkill /IM alamo_*` or `Stop-Process`, which auto mode blocks ("Git Destructive", "Interfere With Workloads") because they can hit other sessions' work. Merging PRs stays blocked on purpose: `dev` -> `main` is Gabriel's call. A rule matches only the spelling written there.
- Default tool access (2026-11-15, `docs/TOOLS.md`): `.claude/settings.json` also pre-approves the build scripts (`build_agent`, `build_module`, `build_msvc`, `build_clang`, `build_asan`, `build_gate`, `build_launcher`), every project script under `tools\` (Python and `.cmd`, `tc.cmd <program>` included), every `roadmap_store.py` subcommand, test executables in the checkout's own `build-*` trees, and git's read and local steps (`add`, `commit`, `merge origin/dev`, ...), so lanes run unattended (2026-11-15; spellings and the list: `docs/WORKFLOW_TIPS.md`, "Unattended runs"). Always asks (`ask` rules): `tc.cmd frida*`, `TTD*`, `cmake*`, `ninja*`, `cargo*` (builds go through the build scripts), `tools\re\ttd_record.cmd`, pushes to `main`, `gh pr merge`. Never runs (`deny`): force pushes, bare `git stash` and `git stash pop`. A `SessionStart` hook runs `worktree_tool.py link --quiet`, which adds the missing `Data` / `extracted` / `toolchain` / `roadmap-store` junctions to an app-made worktree (never replaces a folder, no-op in the main checkout; covered by `--selftest`).
- Writing tests for parallel runs: two ctest entries must not share a fixed `%TEMP%` fixture or output path, including entries that run the same exe with different arguments. Give them separate paths, or a `RESOURCE_LOCK` when they cannot be separated. Treat a flaky failure in one tree as a possible clash first.
- Long determinism tests: don't put a long run under `--check-workers`, which runs each worker count in turn inside one test. Use one ctest entry per worker count: the 0-worker entry writes the CRC log (`--crc-out`, `FIXTURES_SETUP`), the others compare against it (`--golden`, `FIXTURES_REQUIRED`). `alamo_add_worker_count_check` in `engine/CMakeLists.txt` does this; example: `alamo_headless_skirmish_ai_foc_land_outcome` in `engine/apps/CMakeLists.txt`.
- Measured tiers, rotation, flaky retry (wr3 t03-t05, 2026-11-21; replace the hand tiers below as the landing filter): `build_agent.cmd ... <modules>` with no test argument runs the landing tier: every test except the nightly ones of `tools\lint\test_tiers.json` (a test not listed there yet follows its hand `slow` label), via `test_tiers.py exclude` and `ctest --exclude-from-file`. `test_tiers.py regen` rewrites the file from the last nightly run's timings (`gate-dev\build-msvc\ctest_junit.xml`, scaled by the median nightly / landing ratio, 2.53 on 2026-11-21) and lists every test that changes tier: over 30 s goes nightly; a hand-slow test of 5 s or less moves to landing while the estimated landing wall stays under 100 s, unless it compares a stored golden or needs a fixture outside the landing tier. `test_tiers.py check` is the budget lint (landing wall over 180 s or a landing test over 30 s fails, naming the tests); the verifier reports it on every landing. Measured 2026-11-21: landing tier 221 tests, 83 s wall at `-j 4` (fast tier before: 219 tests, 73 s); nightly 114. Worker-count checks (wr3 t04): `ALAMO_WC_SLOT=<k>` leaves out all but the k-th count of each `alamo_add_worker_count_check` group (the 0-worker producer always runs); the verifier rotates k = 0, 1, 2, 3 per landing (`.verifier_wc_slot`), so a divergence at one count is caught within four landings, and the nightly run checks every count. The long runs (16 over 30 s, the 512 s land outcome test among them) stay in the nightly tier. Flaky retry (wr3 t05): every build script except ASan runs ctest through `tools\lint\flaky_retry.py`: a failed test that passes one immediate retry is flaky, does not fail the run, is named on the summary's `flaky:` line and recorded in `<main checkout>\logs\flaky_tests.jsonl`; determinism tests (label `determinism`, set by `alamo_add_worker_count_check`, or a worker-count / golden / CRC / replay / selfcheck / parity-harness name) are never retried. Three flaky runs of one test in seven days file an S2 task in `ngt1` from the verifier or the nightly run (`--report` lists them). The 244 single-test failures of 2026-11-14 to 21: 230 real, 8 flaky (`alamo_jobs_tests` 6, `alamo_core_atomic_file_tests` 1, `alamo_game_bench_stale_scene` 1), 5 environment, 1 unknown. Selftests: `test_tiers.py`, `flaky_retry.py` `--selftest`.

## Worker-count check (OPT3 t07, 2026-11-02)

Rule 3 says per-tick CRCs are identical for every worker count. Every OPT2 / OPT3 / CP / BM change cites this check: name the
scenario(s) it ran and the result in the PR. Two forms, both comparing every count's CRC log with the 0-worker log
(`first_divergence`, which names the first diverging tick and system):
- **Per-process (long runs), CMake** `alamo_add_worker_count_check(<name> COMMAND <exe> [args] [SETUP_ARGS ...] [CHECK_ARGS ...]
  [WORKERS ...] [TIMEOUT s] [SLOW] [PROPERTIES ...])` in `engine/CMakeLists.txt`. One ctest entry per count, so the counts run side by
  side under `ctest -j`: `<name>` runs `--workers 0 --crc-out <bin>/<name>_w0.crc` (`FIXTURES_SETUP <name>_w0`), `<name>_w1`, `_w4`, `_w16`
  and `_w<hardware threads - 1>` (`_w15` on the 16-thread reference PC) run `--workers N --golden` against it (`FIXTURES_REQUIRED`). 16 is
  more workers than logical cores here, so preemption inside a tick is covered too. `SETUP_ARGS` go to the 0-worker entry only (a
  checked-in golden, an `--expect-*` check), `CHECK_ARGS` to the others; `SLOW` labels all entries `slow`. Further entries can compare
  against the same log with `FIXTURES_REQUIRED <name>_w0` and `--golden ${<name>_CRC}`. The command needs `--workers`, `--crc-out`
  and `--golden` (every `alamo_headless` mode has them).

  returns a `WorkerCountReport` (`ok()`, `first`, per-count `vs_first`). Used by `alamo_jobs_crc_tests` (incl. an injected divergence)

## Crash dumps (2026-11-15)

`alamo_game` and `alamo_headless` call `alamo::crash::install()` first thing (`engine/apps/crash`, `[port]`). A crash (access
violation, stack overflow, uncaught exception, `abort`, `std::terminate`, CRT invalid parameter, pure virtual call) writes
`%LOCALAPPDATA%\alamo\crashes\<exe>_<date>-<time>_<pid>.dmp` plus a `.txt` note (reason, exception code, faulting module +
offset) and one `crash: ...` line on stderr; the process exits with the exception code (3 for abort / terminate).
`ALAMO_CRASHDUMP=0` turns it off, `ALAMO_CRASHDUMP_DIR` picks another folder, `ALAMO_CRASH_TEST=<kind>` (access, thread,
stack, throw, abort, terminate, purecall) crashes at start-up to check a build. `alamo_crash_tests` runs every kind in a child.
- **Reading a dump:** `toolchain\re\windbg-1.2611.4001.0\amd64\cdb.exe -z <file.dmp> -y <folder with the exe's .pdb> -c ".ecxr;kn 20;q"`
  (or open it in WinDbg). `.ecxr` switches to the crashing thread's exception context.
- **Symbols:** a normal Release build has no PDBs, so stacks show `exe+offset` only. Configure with `ALAMO_RELEASE_PDB=1` in the
  environment (or `-DALAMO_RELEASE_PDB=ON`): MSVC `/Z7` + `/DEBUG /OPT:REF /OPT:ICF`, a PDB next to each exe. A dump needs the PDB of
  the exact build that crashed. Test builds carry them, other trees do not (`docs/DECISIONS.md`, "Release symbols"):
  `package_testbuild.py` refuses a tree without fresh PDBs and writes `dist/<name>_symbols.zip` beside the player's zip.
- In-process by design: the dump thread is created at start-up and uses fixed buffers, but `MiniDumpWriteDump` itself allocates,
  so a crash that corrupted the heap can still lose its dump (the `.txt` note says `FAILED`). A dump from the Command Center as
  a separate process would avoid that; not done.

## Test support headers (CU4, 2026-11-07)

Header-only INTERFACE targets; link them from a test exe, never from an engine library.
- `alamo_test_support` (`engine/test_support`): `alamo/test/support.hpp` has `CHECK` (prints `FAIL <file>:<line>: <expr>`,
  counts in `alamo::test::g_fail` / `g_checks`), `section`, `report`, `env_or_empty` / `env_or`, `foc_data_root` /
  `eaw_data_root`, `print_skip`, `write_file` / `read_file` and `kSkipReturnCode` (77); `alamo/test/thread_parallel_for.hpp`
  is the pool above. A test file includes it and puts `using ::alamo::test::g_fail;` where its counter was; main() keeps its
  own summary line and exit code. The counters are inline variables: one per exe, whichever TUs include the header.
  `CHECK` prints the file's basename (`std::source_location`, 2026-11-14), never `__FILE__`; a test file with its own check macro
  uses `ALAMO_TEST_FILE()` from the same header, so the macro text does not change with the checkout path.
  Test exes stay one per scenario family (Gabriel, 2026-11-14, bo2): merging them into runners was measured and dropped, since relinking
  all 135 exes takes 4.5-8.1 s and merging saves nothing on compiling (`docs/PERFORMANCE.md`, "Test executables: inventory";
  `python tools/analysis/exe_inventory.py` redoes the table). To add a test: new `alamo_add_test`-style exe in the module's CMake file
  with its own `add_test`, as the neighbouring ones.
- `alamo_render_test_support` (`engine/render/test_support`): `alamo/render/test/gpu.hpp` has `GpuCore` (ctx / alloc / up /
  ring; derive to add a renderer, HUD or timer) and `OffscreenWithDepth` / `OffscreenColorOnly` over
  `alamo/render/offscreen.hpp` (the render library's offscreen target, also used by the `alamo_render` sub-mains through
  `engine/render/app/app_common.hpp`).

## Claude Code setup (2026-11-13)

- Skills (`.claude/skills/<name>/SKILL.md`, invoked as `/<name>` or picked by Claude from their descriptions): `build`, `start-group`,
  `finish-group`, `phase-status` (the former `.claude/commands`), plus `behaviour-check` (the `Behaviour:` trailer and the

- C++ code intelligence: the project-local plugin `eaw-clangd` (marketplace `tools/claude_plugins`, enabled in `.claude/settings.json`)
  gives Claude clangd diagnostics after each edit and an `LSP` navigation tool. It runs `python -I tools/lsp/clangd_launch.py`, which
  starts `toolchain\llvm\bin\clangd.exe` with the MSVC environment of `toolchain\msvc\setup_x64.bat`. The compile database comes
  from `.clangd` at the checkout root: `build-wt-clang\compile_commands.json`, relative to that file, so each worktree reads its own
  tree (2026-11-19). Claude Code starts the launcher from the main checkout even in a worktree session (`CLAUDE_PROJECT_DIR` and its
  cwd are the main checkout), so the launcher no longer picks a tree itself. `build_agent.cmd clang all configure` writes the database
  in about 5 s without building (`/start-group` step 4). Run it before clangd opens a C++ file: a file opened earlier keeps
  fallback flags (false include errors, references missing) until the session restarts. Without it, `findReferences` on
  `TacticalBattle::issue_orders` found only the declaration; with it, the calls in `battle_ai.cpp` and
  `tactical_battle_services.cpp` and the definition, once the background index (about 2 minutes, `build-wt-clang\.cache\clangd`) was done.
  `python -I tools/lsp/clangd_launch.py --check <file>` is a one-shot diagnostics run (its `ExtractFunction` tweak
  "errors" are clangd's refactoring self-test, not compile errors); `--print` shows the command. The plugin loads after the folder is
  trusted; if diagnostics are missing, check the `/plugin` errors list.
- Read-only allowlist (2026-11-13, from transcript frequencies): PowerShell `Get-Content`, `Get-ChildItem`, `Select-String`,
  `Test-Path`, `Measure-Object`; `roadmap_store.py lint`, `backlog list`, `claims`, `--help`; `clangd_launch.py --check` / `--print`.
  Cmdlets that take script blocks (`Where-Object`, `ForEach-Object`, `Select-Object` with calculated properties) are left out on purpose.
